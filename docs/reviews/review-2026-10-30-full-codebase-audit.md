## Summary
Reviewed the entire backend (`backend/src/app`, `backend/tests`) and frontend (`frontend/src`) against `.claude/rules/*.md` and the CLAUDE.md architecture/standards. The codebase is in good shape overall: layering is respected in nearly all routers/services/repositories, Pydantic schemas consistently use `extra="forbid"`, ownership/role checks are enforced in the service layer, categories are data-driven (no hardcoded category logic), the extraction strategy interface is used correctly, and the frontend consistently follows the TanStack Query / Zustand / RHF+Zod / shared-Axios-client conventions with accessible form markup. All static checks pass except a few dependency-vulnerability findings. Found 2 mandatory issues, 5 recommended improvements, and 3 nitpicks — no business-logic-in-routers, no missing role checks, and no cross-tenant ownership leaks were found.

## Mandatory
- `backend/src/app/dependencies/auth.py:32` — `get_current_user` runs a raw `select(User).where(User.email == email)` query directly against the session instead of calling `UserRepository.get_by_email` (which already exists in `backend/src/app/repositories/user_repository.py:17` and does exactly this). This violates backend-python.md ("Put all DB access in repositories/... Never query the DB from a router or service directly") and the CLAUDE.md one-way layering rule, and duplicates logic that already exists. Fix: inject/construct a `UserRepository` here and call `get_by_email`.
- `backend/src/app/services/categorization_service.py:157` (`_suggest_via_llm`) — instantiates `anthropic.AsyncAnthropic(**client_kwargs)` directly inside the service method on every LLM-fallback call, rather than receiving the client via `Depends`/constructor injection. This violates backend-python.md: "Inject dependencies (DB session, current user, services, clients) via Depends — never instantiate external clients (HTTP, storage, LLM/OCR) inside business functions." Contrast with `ClaudeExtractor` (`backend/src/app/extraction/claude_extractor.py:89-96`), which correctly builds its client once in `__init__` and is wired via `Depends(get_extractor)`. Besides the layering violation, this also creates a new HTTP client per receipt upload, which is wasteful. Fix: build/inject the Anthropic client once (e.g. via a constructor param or a `Depends`-provided factory) and reuse it.

> A third mandatory finding from the reviewing subagent — a `mypy --strict` failure at `backend/src/app/core/security.py:39` ("Returning Any from function declared to return `str`") — was independently re-run twice directly against this project's configured environment (`mypy --strict src` and again with `--no-incremental`) and did **not** reproduce; both runs report "Success: no issues found in 47 source files". PyJWT 2.13 (the installed version) ships inline type annotations (`py.typed`), so `jwt.encode(...)` already types as `str`, not `Any`. This finding has been removed from Mandatory as not reproducible; retained here only for traceability.

## Recommended
- `backend/src/app/repositories/category_repository.py:7` — `CategoryRepository` imports `CategoryOption` from `app.services.categorization_service`, i.e. a repository depending on the services layer. This inverts the declared one-way dependency flow (`routers -> services -> repositories`). Recommend moving `CategoryOption` (and the `CategoryProvider` Protocol it supports) into `schemas/` or a dedicated port module so repositories don't import from services.
- `backend/src/app/services/receipt_service.py:190-204` (`update`) — `ReceiptUpdate.category_id` is applied via `setattr` with no check that the category exists (or is active). SQLite does not enforce FK constraints by default here (no `PRAGMA foreign_keys=ON` in `db/session.py`), so an arbitrary/nonexistent `category_id` would silently persist a dangling reference. Recommend validating the category (via `CategoryRepository.get_by_id`, mirroring the existing `_get_or_404` pattern in `category_service.py`) before accepting it.
- `backend/pyproject.toml` (direct deps `pyjwt>=2.9`, `pillow>=10.4`) — `pip-audit` (run against the active interpreter) flags the installed versions: `pyjwt 2.13.0` has multiple known CVEs (fixed in 2.14.0/2.15.0) and `pillow 12.3.0` has numerous CVEs (fixed in 13.0.0). Both are direct project dependencies and used for security-sensitive code paths (JWT signing, image handling). Recommend bumping the minimum pins. Note: `pip-audit` also flagged many other packages (`mcp`, `opentelemetry-api`, `ujson`, `setuptools`, `pip`, `pyasn1`, `urllib3`, `werkzeug`) that are not declared dependencies of this project (`pyproject.toml` has no reference to them) — these appear to be ambient/tooling packages in the shared interpreter, not part of this project's footprint, and are not actionable findings here.
- `frontend/package.json` — `npm audit` flags `react-router-dom@^6.26.0` (open redirect / SSR hydration advisories) and `zod@^3.23.8` (DoS via oversized constrained collections), both with fixed major versions available. Both are approved libraries per CLAUDE.md, so this is a version-bump decision rather than a library-choice issue; recommend scheduling the upgrade (noting both fixes are breaking-change major bumps per `npm audit`).
- `frontend/src/features/auth/hooks/useAuth.ts:17-21` — in `useLogin`'s `mutationFn`, `setToken(token)` is called (persisting to localStorage via the Zustand `persist` middleware) *before* `authService.getCurrentUser()` has succeeded. If the `getCurrentUser` call then fails, a bearer token is left persisted in storage without a confirmed user/session, leaving the store in a partially-authenticated state. Recommend returning `{ token, user }` from `mutationFn` only after both calls succeed, and calling `setSession` solely in `onSuccess` (drop the early `setToken` call).

## Nitpick
- `backend/src/app/models/receipt.py:41`, `backend/src/app/schemas/receipt.py:34`, `backend/src/app/extraction/validation.py:44` — `needs_review: bool` doesn't use one of the prescribed boolean prefixes (`is_`, `has_`, `should_`, `can_`) from backend-python.md. Used consistently throughout, so low priority (e.g. rename to `should_review` if ever touched).
- `frontend/src/features/receipts/components/ReceiptReviewForm.tsx:96` — line is 101 characters, one over the 100-char limit in frontend-react.md (`helperText` ternary for the merchant-name field).
- `backend/src/app/core/config.py:33` — the default dev `jwt_secret_key` ("change-me-in-development-only") is 29 bytes, which triggers PyJWT's own `InsecureKeyLengthWarning` (observed during the test run) for HS256's 32-byte recommendation. Harmless since `.env.example` already documents replacing it with "a long random value" for real use, but a longer placeholder would avoid the warning noise in dev/test logs.
